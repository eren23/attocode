# Eval matrix R1: the first full run

**Status: A paid rerank of the first 48 product files with Jev gave the
largest gain. On the core mix, file Acc@5 is 0.594 against 0.425 for
`product` (+0.169, 66 wins and 5 losses, 360 issues from 208 repositories).
The fusion of product search with the dense arm gave +0.083. The
repo-map order gave +0.028 with no losses, but only because it leaves out
test files, as the gold rule does. Haiku 4.5 over 24 files gave
+0.122 at 18 times the cost of Jev, and 9% of its answers were not usable.
Neither harness check gave its published number. Thus compare cells only
inside this matrix, not with numbers from papers.**

## What we ran

- **Code.** The product source of commit `72872ed` (release-gate engine hash
  `cf9c737a452b`), and the eval code of `3bf58d2` (dense v2, #136).
- **Instances.** 2,579 instances of 10 datasets at 2,366 (repository,
  commit) snapshots. One SWE-bench Lite snapshot failed, so 2 of its rows
  have no result.
- **Queries.** The full issue, and the title where a dataset has titles
  (lca, lite, live, locbench and polybench). The case packs have one query
  each. `locbench_title` is the older pack of 42 Loc-Bench issues with the
  title as the query.
- **Cells.** The free first-stage cells ran on all instances. The dense
  cells ran on the core mix and on Loc-Bench 560. The paid rerank cells ran
  on the core mix (396 instances), with the full issue and the `product`
  pool only.
- **Computers.** The Mac made 1,217 snapshot groups. A rented pod made the
  other 1,149 groups for $1.77 (CPU work only). A GPU pod made the dense
  vectors for $2.92. The paid calls went from the Mac through OpenRouter.

The pod and the Mac must give the same results for the same tree. In a
check of 100 results from 10 groups, 19 of the first 92 were different. The
product keeps the `os.scandir` order for files of equal importance, and then
it cuts the list at a cap. macOS and Linux list a folder in different
orders. After the pod used the macOS order, 97 of 100 results were equal.
The other 3 are one query, and they are different only below rank 48.

- **Repo map.** `repomap` won against `product` on every large dataset:
  5/0, 15/1, 11/0, 13/4 and 4/0 wins and losses. The Holm correction covers
  the 80 tested comparisons of this report, so only live passes alone (p 0.047).
  The gain comes from one rule: the repo map leaves out test files. The gold
  files of these datasets come from the non-test part of each patch. The
  `product` list without its test files gives the same values (lca 0.347,
  lite 0.712, live 0.220, locbench 0.552, polybench 0.262). On the core
  mix, `repomap` is equal to that list (1 win and 1 loss). Jev over 48
  files gains +0.142 over that list (59 wins and 8 losses).
- **Importance weight.** `product_noimp` is within 0.007 of `product` on each
  dataset. This agrees with the
  [2026-10-09 correction](2026-10-09-locbench-560-first-stage.md) on four more
  datasets.
- **Query expansion.** `product_auto` is lower on each dataset, by 0.006 to
  0.023.
- **Grep.** The agentic-grep stand-in beat `product` on lca, live and
  polybench, and it lost on lite and locbench. No difference passes Holm.
- **Dense.** On Loc-Bench 560, `dense` gave +0.070 (Holm p 0.019) and
  `rrf(product+dense)` gave +0.146 (p 0.0006). The README section "Matrix
  dense arm" has the details.
- **Title query.** With the title, `product` gives 0.307, 0.555, 0.234, 0.498
  and 0.275. On live and polybench, the title is better than the full issue.

Two cells can give an empty list. These are not ranking results.
`filebm25` runs only for a query of 20 or more tokens, and `grep` needs
code-like terms. Thus both cells are empty for all case-pack queries, and
`filebm25` is empty for almost all titles. On the full issue, 2% to 8% of
their lists are empty, and an empty list scores 0.

## Noise floor

The `noise50` subset (50 core instances) ran each paid cell three times.
Jev over 24 files gave the same metrics in all three runs. Jev over 48
files was different on one value only (gNDCG@5 0.873 and 0.884 on
`graded_blind`). The first two Haiku runs gave the same metrics. The third
Haiku run is not a measurement: 46 of its 50 calls failed (see below).

## Harness checks

| Check | Published | This harness |
|---|---:|---:|
| BM25, SWE-bench Lite 274, file Acc@5 (`filebm25`) | 61.68 (LocAgent) | 52.2 (45.1 to 60.2) |
| CodeRankEmbed, Loc-Bench, Python files only, Acc@5 (`dense`) | 74.29 (SweRank) | 61.4 |

Neither check passes. `filebm25` is the whole-file BM25 list of the
product, and 19 of the 274 issues are too short for it. The cause of each
gap is not known. Within the matrix, all cells use the same snapshots,
gold files and scorer. Thus the differences between cells hold, but the
absolute values are not comparable with the papers.

## Failures and spend

- **OpenRouter.** $5.04 by the usage counter of the provider. The matrix
  ledger counted $6.07, because it counts each call at an upper estimate.
  The cap was $10.
- **Haiku 4.5.** 39 invalid answers. 57 request failures: 46 refusals
  (HTTP 403) when the OpenRouter key reached its own $15 limit in the third
  noise run, and 11 timeouts and dropped connections.
- **Jev.** 4 timeouts.
- **RunPod.** $1.77 for the retrieve stage and $2.92 for the dense vectors.

## What this does not show

- No single core dataset passes Holm alone. Each has 20 to 80 instances,
  and the core report tests 115 comparisons. Use the pooled table.
- The paid cells ran only on the full issue and only on the `product`
  pool. A rerank of `rrf(product+dense)` did not run.
- The local cross-encoder cells of the registry (Qwen3, bge and gte
  rerankers) did not run. They need a GPU pod.
- Main now has #135, which changes the MCP tool list. It does not change
  search, but it changes the engine hash. A new run makes new results.

## Reproduce

From a checkout with the product source of `72872ed` and the eval code of
`3bf58d2` (`PYTHONPATH=.:packages/code-intel/src`):

```bash
OUT=~/Documents/AI/attocode-evals/matrix/runs/r1
python -m eval.matrix.run status $OUT
python -m eval.matrix.run run $OUT --stage rows
python -m eval.matrix.run run $OUT --stage rerank --arms jev-choice,haiku45-listwise --budget-usd 10
python -m eval.matrix.run report $OUT --cells product,product_noimp,product_auto,kw,body,filebm25,chunkrrf,grep,repomap --baseline product --output $OUT/report-free.md
python -m eval.matrix.run report $OUT --ids eval/matrix/core_ids.txt --baseline product --output $OUT/report-core.md --cells 'product,repomap,grep,dense,rrf(product+dense),product>jev-choice.24,product>jev-choice.48,product>haiku45-listwise.24'
```

The snapshot and retrieve stages ran with `--stage snapshot` and
`--stage retrieve` in shards on the Mac and the pod. The dense vectors came
from `python -m eval.matrix.dense` on a GPU pod. The cached results make a
rerun of the rows and report stages free. The run folder keeps the four
full reports: `report-free.md`, `report-core.md`, `report-noise50.md` and
`report-lb560.md`. The pooled table comes from `stats.paired` on the rows of
`results.jsonl`.
