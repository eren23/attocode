# Loc-Bench V1: all 560 instances

**Status: Jev `choice` over a lexical and BM25 candidate pool reached file Acc@5
0.757 with the full issue as the query. That is inside the published range
(0.743 to 0.870), but below the best systems.** Lexical search alone gives
0.377. Jev over the lexical pool gives 0.698. Adding file-level BM25 to the
pool raised the share of instances with every gold file in the first 48
candidates from 0.759 to 0.832, and Jev kept about 91% of that ceiling. Search
now fuses whole-file BM25 for queries of more than 20 words. With it, lexical
search with the importance and frecency weights at zero gives 0.529, and Jev
over 48 files gives 0.752
([product change](#product-change-whole-file-bm25-fusion)). With the default
weights, lexical search gives 0.532 ([first-stage arms](2026-10-09-locbench-560-first-stage.md)).

## What we ran

- **Dataset.** [Loc-Bench V1](https://huggingface.co/datasets/czlll/Loc-Bench_V1)
  at revision `c44cf3b74e07ca642cec841b471a9939907c12a7`. It has 560 Python
  instances from 165 repositories: 242 bug reports, 150 feature requests, 139
  performance issues, and 29 security issues. We kept all 560 rows.
- **Query.** The full issue (`problem_statement`), as in the published
  systems. We also ran the first line of the issue (the title), which is the
  query form of our [42-instance check](2026-10-08-blind-graded-rerank.md). Ten
  issues have only one line, so their title query is the full issue.
- **Gold.** The unique files in `edit_functions`, as in the LocAgent
  evaluation code. 484 instances have one gold file, 44 have two, 25 have
  three, 6 have four, and 1 has five.
- **Metric.** LocAgent file Acc@k: a hit when the first k files hold
  min(|gold|, k) gold files. No instance has more than five gold files, so
  Acc@5 is also strict Acc@5 (all gold files in the first five). The two
  values were equal in every arm.
- **Lexical.** The product's lexical search on a fresh worktree at
  `base_commit`, with the importance and frecency weights at zero. The
  product default sets the importance weight to 0.5
  ([first-stage arms](2026-10-09-locbench-560-first-stage.md)). It reads 400 chunks and keeps the first 48
  distinct files. Its order equals the order of the default broad-query
  rerank in all 1,110 queries.
- **BM25.** Okapi BM25 (k1 1.2, b 0.75) over whole Python files at
  `base_commit`, with the product's term rule (`focused_evidence.terms`, with
  counts). It keeps the first 48 files.
- **Fused.** Reciprocal-rank fusion (k 60, equal weights) of the lexical and
  BM25 orders, 48 files. We fixed this rule before any run.
- **Jev.** `typesafe/jev-1.13` `choice` through OpenRouter reorders the first
  24 or the first 48 files of a pool. Each candidate is a query-focused
  excerpt of at most 1,350 characters, with the product's excerpt rule. The
  48-file arms ran on the full issue only.

## Correction to the first run

The first version of this report (PR #114) gave 0.671 for Jev over the
lexical pool at 48 files, and it said that no Jev request fell back. That was
wrong. The `jev-choice` trial sends one request per query. When the request
fails, every candidate gets 0.5 and the query keeps the lexical order, but the
trial did not set a fallback reason. In the first run, 135 of 1,670 requests
failed this way (85 at 24 files, 50 at 48 files). The trial now marks these
queries as `request_failed`, and the scorer counts them from the old files too.

The results above come from a second run on the same pools. It also uses the
product's excerpt rule. In this run, 8 of 3,340 requests failed. They are the
four longest issues (28,000 to 55,000 characters) with 48 candidates, and they
failed in both the lexical and the fused arm.

Jev is not fully deterministic. On 356 queries with the same input in both
runs and no failure, 194 rankings were the same. Acc@5 changed for 1 query.
Of the 13 Acc@5 changes between the runs on otherwise identical input, 12 came
from failed requests.

## Cost and time

  Other use of the same key in these windows also counts.
- In the second run, the median Jev latency was 470 ms with 24 files and

- BM25 over the Python files took at most 0.8 s per instance (two queries).

- Two zulip instances failed to clone in the first run because of network

## Product fix: rare words for source-body search

Source-body search sends at most 20 words to FTS5. Before this fix, it sent
the first 20 in alphabetical order, so a long issue searched with words such as
"able" and "about". The search now keeps the 20 words that the fewest source
chunks contain. Queries with 20 words or fewer do not change: this includes
every title and every blind-pack query. The change affects 522 of the 560 full
issues.

We built all 560 lexical pools again with the fix and ran Jev and the BM25
fusion again on them. All 550 separate title pools came out identical.

| Full issue | Before | After | Paired change (wins, losses) | Range of change |
|---|---:|---:|---|---|
| Lexical Acc@5 | 0.377 | 0.388 | +0.011 (66, 60) | −0.040 to +0.065 |
| Every gold file in the first 48 | 0.759 | 0.784 | +0.025 (31, 17) | +0.002 to +0.049 |
| Lexical pool, Jev over 48 files | 0.698 | 0.721 | +0.023 (33, 20) | −0.002 to +0.049 |
| Fused pool, no reranker | 0.511 | 0.521 | — | — |
| Fused pool, Jev over 48 files | 0.757 | 0.763 | — | — |

The fix adds gold files to the pool, but the gain at Acc@5 is not clear.

Most of the BM25 gain stays after the fix. On the fixed pools, fusion still raised
Acc@5 from 0.388 to 0.521 without a reranker (106 wins, 31 losses), and from
0.721 to 0.763 with Jev over 48 files (41 wins, 18 losses). The lexical arm
orders files by their best chunk, and BM25 scores whole files. Two separate Jev
runs over the same fixed lexical pool gave the same Acc@5 (0.721).

## Product change: whole-file BM25 fusion

Search now ranks whole source files with BM25 for a query of more than 20
words, such as a pasted issue. The source-body index keeps one FTS5 row per
source file. Docs and data files (Markdown, text, reStructuredText, JSON, YAML,
TOML, and similar) stay out of this table. Search then fuses two file orders
with equal-weight RRF (k 60), each cut to 48 files: the lexical file order and
the BM25 order. This is the rule of the fused eval arm. A query with 20 words
or fewer does not change.

We built all 560 pools again with this change and ran Jev on them. All 550
separate title pools and all 38 full issues with 20 words or fewer came out
identical. The change affects the other 522 full issues. "Before" is the
body-fix run in the previous section.

| Full issue | Before | After | Paired change (wins, losses) | Range of change |
|---|---:|---:|---|---|
| Lexical Acc@5 | 0.388 | 0.529 | +0.141 (91, 12) | +0.100 to +0.179 |
| Every gold file in the first 48 | 0.784 | 0.827 | +0.043 (39, 15) | +0.012 to +0.071 |
| Lexical pool, Jev over 24 files | 0.641 | 0.714 | +0.073 (59, 18) | +0.040 to +0.107 |
| Lexical pool, Jev over 48 files | 0.721 | 0.752 | +0.031 (39, 22) | −0.002 to +0.061 |

The lexical gain is clear. The gain with Jev over 48 files is not clear over
all 560 instances, because its range includes zero.

Both runs have the importance and frecency weights at zero. With the default
weights, lexical Acc@5 is 0.532 on the full issue (5 wins and 3 losses
against 0.529).

The product result is near the fused eval arm. Lexical Acc@5 is 0.529 against
0.521. The share with every gold file in the first 48 is 0.827 against 0.839.
Jev over 48 files gives 0.752 against 0.762.

The two differ in three ways. The product BM25 covers every source language, not only Python. It uses the
body-search word rule. It sends at most 64 words, the rarest first.

### Two earlier versions and the held-out part

We stopped two earlier versions after part of a run:

- **All files.** The first version indexed docs and data too. A long prose
  issue matches docs well, so 1,664 non-code files entered the first 48 files
  of 199 pools (8.4 per pool). On these instances, the share with every gold
  file in the first 48 fell from 0.854 to 0.819 (4 wins, 11 losses).
- **Chunk-rank fusion.** The second version added a BM25 score (k 20) to the
  best chunk of each file. Chunk ranks spread over many chunks per file, so
  BM25 got more weight than the lexical list. On 150 instances, Jev over 48
  files fell from 0.780 to 0.753 (5 wins, 9 losses).

We chose both fixes after we saw results on 199 instances. The other 361
instances are a held-out part:

| Held-out full issues (361) | Before | After | Paired change (wins, losses) | Range of change |
|---|---:|---:|---|---|
| Lexical Acc@5 | 0.357 | 0.518 | +0.161 (65, 7) | +0.107 to +0.213 |
| Every gold file in the first 48 | 0.745 | 0.806 | +0.061 (29, 7) | +0.025 to +0.094 |
| Lexical pool, Jev over 24 files | 0.632 | 0.718 | +0.086 (44, 13) | +0.043 to +0.132 |
| Lexical pool, Jev over 48 files | 0.704 | 0.753 | +0.049 (30, 12) | +0.010 to +0.088 |

On the 199 instances that we saw, Jev over 48 files had 9 wins and 10 losses.

## The product query cut (512 characters)

The product ranker (`SystemOneChoiceReranker`) sends only the first 512
characters of the query to the ranking endpoint. The Jev arms above sent the
full issue. 465 of the 560 issues are longer than 512 characters. The median
length is 1,386 characters, and one issue in ten has more than 5,378.

We ran Jev again on the 465 long issues, with the query cut to 512
characters. The run used the frozen pools of the whole-file BM25 run and the
same candidates. We built the excerpts again from the base commit. Every
excerpt set had the same hash as in the first run, so the query is the only
change.

| Long full issues (465) | Full query | First 512 characters | Paired change (wins, losses) | Range of change |
|---|---:|---:|---|---|
| Jev over 24 files | 0.710 | 0.692 | −0.017 (4, 12) | −0.036 to 0.000 |
| Jev over 48 files | 0.753 | 0.746 | −0.006 (7, 10) | −0.026 to +0.011 |

Over 48 files, Jev failed on 8 of these requests in the first run and on 1 in
this run. A failed request keeps the pool order. Without the 9 instances with
a failure, Jev over 48 files goes from 0.761 to 0.750 (5 wins, 10 losses).

Both arms lose one to two points, but no range excludes zero. The cut changes
the first five files of most issues, but it rarely changes whether every gold
file is among them. A longer limit costs little, because the request already
carries up to 24 excerpts of 1,350 characters each. We did not change the
product limit. A new limit needs a test on fresh queries first.

The run cost $0.58 and took less than 10 minutes with four workers.

## Limits

- **Query length.** The Jev arms sent the full issue. The product cuts the
  ranking query at 512 characters, and 465 of the 560 issues are longer than
  that. With the cut, Jev loses one to two points on these issues (see the
  previous section). The title arm is under the limit (the longest title has
  159 characters).
- **Contamination.** Loc-Bench uses public GitHub issues, and 194 non-bug rows
  are older than October 2024. Jev may have seen some of these fixes in
  training.
- **Labels.** The gold files are the files that the fix edited. Other files
  can also be relevant, so the metrics count some useful answers as misses.
  MULocBench flags 10 rows as invalid. We kept them, as the published 560
  numbers do.
- **One run per arm.** Jev changed Acc@5 on 1 of 356 repeated queries, so
  this is a small effect. We did not repeat the full runs.
- **Language.** Loc-Bench is Python only.

## Reproduce

Jev sends source excerpts from these public repositories to OpenRouter. It
needs `OPENROUTER_API_KEY`. The work directory needs about 5 GB per worker.

Commit `5b67651` is the last commit with the scripts that built the pools of
this run (`eval/locbench560/run.py prepare` and `shard`, and
`eval/locbench560/first_stage.py`). Now, `run.py shard` runs Jev on the
frozen pools in `$LOCBENCH_DIR/pools/`, and the eval matrix makes the first
stage again. The matrix cell `product_noimp` gives the same file order as
the frozen lexical pools (cell `lexical`). The matrix cells `filebm25` and
`chunkrrf` come from the product search. They are not the eval BM25 and
fusion arms of this run.

```bash
export LOCBENCH_DIR=~/locbench560
uv run --with datasets python eval/locbench560/run.py fetch   # writes all.json
.venv/bin/python eval/locbench560/run.py shard 0 2   # Jev on the frozen pools; run "shard 1 2" in a second shell
.venv/bin/python -m eval.matrix.run import-legacy scores --locbench $LOCBENCH_DIR
.venv/bin/python -m eval.matrix.run run scores --stage snapshot
.venv/bin/python -m eval.matrix.run run scores --stage retrieve --shard 0/3   # also shards 1/3 and 2/3
.venv/bin/python -m eval.matrix.run run scores --stage rows
.venv/bin/python -m eval.matrix.run report scores --baseline lexical   # writes scores/report.md
```

The snapshot and retrieve stages keep their results in
`~/Documents/AI/attocode-evals/matrix/`, so a second run uses them again.
`status scores` shows the coverage. The import writes `results.jsonl` again,
so run the rows stage after each import.

The report refuses a cell that has no row for some instances. Select the
complete cells with `--cells`, or score a part with `--ids`.

To compare two finished runs instance by instance, import both, and give one
of them a prefix. Then pair the cells. `--ids` takes a file with one instance
id per line, for a part such as the held-out instances:

```bash
.venv/bin/python -m eval.matrix.run import-legacy both --locbench before=BEFORE_DIR --locbench AFTER_DIR
.venv/bin/python -m eval.matrix.run report both --cells lexical,jev48 --pair lexical:before.lexical \
  --pair jev48:before.jev48 --metric acc5 --metric ceil48 [--ids IDS_FILE]
```

To run Jev again on a finished run with the product query cut, use the `q512`
command. It clones each repository again, checks out only the candidate files,
and writes `trials-q512/`. The import makes the cells `jev24_q512` and
`jev48_q512`. They cover only the long issues. Import the run again, and
score these cells with the ids of the long issues:

```bash
.venv/bin/python eval/locbench560/run.py q512 0 4   # also shards 1, 2, and 3
ls $LOCBENCH_DIR/done-q512 | sed 's/\.json$//' > long_ids.txt
.venv/bin/python -m eval.matrix.run import-legacy scores --locbench $LOCBENCH_DIR
.venv/bin/python -m eval.matrix.run report scores --ids long_ids.txt --cells jev24,jev48,jev24_q512,jev48_q512 \
  --pair jev24_q512:jev24 --pair jev48_q512:jev48 --output scores/q512.md
```

Both drivers resume from their done markers. An instance with a failed trial
gets no marker, so the next run retries it. To retry a clone or checkout
failure, delete its marker and run the same driver with `only <instance_id>`.
