# Function units in a lexical ranker (2026-10-19)

**Status: rejected. On Loc-Bench 560, BM25 over function units does not
beat BM25 over 40-line windows of the same files. Fused with `product`,
the function list beats the window list by +0.018 Acc@5 (27 wins, 17
losses, Holm p 0.364). The frozen rule needed +0.02 with p below 0.05.
Thus this test gives no reason to add function-body documents to product
search. A second analysis corrects the
[2026-10-18 report](2026-10-18-locbench-remeasure.md). The CodeRankEmbed
gain of `fn-dense` over `dense` has two parts: the function unit (+0.055)
and the corpus rule (+0.082).**

## The question

`fn-dense` (CodeRankEmbed over function units) gave 0.739 Acc@5, and
`dense` (CodeRankEmbed over 40-line windows) gave 0.602. `fn-dense` needs a
GPU. This test asks whether the function unit also helps a CPU ranker. If
it helps, product search can add one document for each function body.

## What we ran

- **Code.** `main` at `e440d06`. The script is
  `eval/matrix/function_bm25.py`.
- **Instances.** Loc-Bench V1, 560 instances, the full issue as the query,
  and the snapshots of the 2026-10-18 run.
- **Files.** Both arms read the same files: the `.py` files with at least
  one function unit under the rule of `eval/matrix/function_dense.py`. This
  rule keeps no file with "test" in its path. For pytest-dev repositories,
  only the file name counts.
- **Arms.**
  - `fn-bm25`: one document for each function unit, with the SweRank text
    (id, class line, source). This gives 3,070,649 documents, the same
    count as the `fn-dense` corpus.
  - `win-bm25`: one document for each 40 lines of the same files, with
    "File: <path>" first. This gives 2,317,856 documents.
  - `rrf(product+fn-bm25)` and `rrf(product+win-bm25)`: `eval.matrix.arms.rrf`
    (k 60, the first 48 files of each list) over the 2026-10-18 `product`
    rows and the BM25 list.
- **Ranker.** The product tokenizer (`_tokenize`) and the product BM25
  parameters (k1 2.2, b 0.3). The ranked documents give the files in the
  order of their first document, up to 200 files.
- **Computer.** The Mac, 4 workers, 191 seconds. The run read the cached
  snapshots and wrote no new snapshot data.

## Frozen rule

We wrote the rule before the run (frozen 11:54:02, run start 11:54:15).
The change is build-worthy only if both conditions are true:

1. `rrf(product+fn-bm25)` − `rrf(product+win-bm25)` ≥ +0.02 Acc@5, with
   Holm p < 0.05.
2. `rrf(product+fn-bm25)` − `product` ≥ +0.03 Acc@5, with Holm p < 0.05.

Condition 1 isolates the unit, because both lists come from the same
files. Condition 2 alone can pass from the corpus rule. No parameter
changed after the run. The frozen script had SHA-256 `64c585bc…`. After
the run, a Ruff fix sorted one import block, and the committed script has
SHA-256 `75fba3de…`. This fix does not change the output.

Condition 1 fails and condition 2 passes, so the decision is a rejection.
Alone, function units score below windows (40 wins, 45 losses). The
fusion with `product` gains in both arms. Most of that gain comes from a
second list without test files and non-Python files, not from the unit.

Two instances (`Innopoints__backend-124`, `Standard-Labs__real-intent-102`)
give empty BM25 lists in both arms, because no query term occurs in their
files. They count as misses in both arms.

## Correction to the 2026-10-18 report

The 2026-10-18 report said: "Thus function units explain the R1 gap."
That sentence is too strong. `fn-dense` differs from `dense` in two ways:
the unit (functions against 40-line windows) and the corpus (non-test
`.py` files against all files). A post-hoc analysis applies the same
corpus rule to the ranked lists of the 2026-10-18 run. The rule removes
none of the 676 gold files of Loc-Bench 560.

| Cell | All files | Corpus rule | Δ | Wins / losses | p (Holm) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `dense` | 0.602 | 0.684 | +0.082 | 46 / 0 | 0.0007 |
| `product` | 0.566 | 0.593 | +0.027 | 15 / 0 | 0.0007 |
| `kw` | 0.495 | 0.511 | +0.016 | 9 / 0 | 0.067 |
| `body` | 0.259 | 0.373 | +0.114 | 64 / 0 | 0.0007 |
| `chunkrrf` | 0.414 | 0.523 | +0.109 | 61 / 0 | 0.0007 |
| `rrf(product+dense)` | 0.713 | 0.729 | +0.016 | 17 / 8 | 0.137 |
| `fn-dense` | 0.739 | 0.739 | 0 | 0 / 0 | |

The fused row fuses the two filtered lists. `fn-dense` does not change,
because its corpus already obeys the rule. Against filtered `dense`,
`fn-dense` gains +0.055 (58 wins, 27 losses, Holm p 0.002). The p-values
come from one report with Holm over these seven comparisons. Thus:

- The function unit gives +0.055 with an embedding model. With BM25, it
  gives no gain.
- The corpus rule gives +0.082 to `dense`. The rule fits Loc-Bench, because
  its gold never holds test files or non-Python files. In the first five
  files, `dense` returns 1.72 test files on average and `product` returns
  0.14. Product search cannot drop test files or non-Python files in
  general, so this gain is a property of the benchmark, not a product
  opportunity.

## Limits

- **One dataset.** Loc-Bench V1 is Python only. A function unit can behave
  differently in other languages.
- **One BM25 setting.** The test used the product parameters, and no
  tuning. Other parameters or a field-weighted function document can give
  a different result.
- **Fusion depth.** The fusion uses the first 48 files of each list, as
  every matrix fusion does.
- **Post-hoc filter.** The corpus-rule table is a post-hoc analysis, not a
  frozen trial.

## Reproduce

1. Run `python eval/matrix/function_bm25.py WORK CODE CACHE INSTANCES 4`
   with the `instances.jsonl` of the 2026-10-18 run.
2. Add the `fn` and `win` lists of `WORK/fn-bm25.json` as rows, and fuse
   each with the `product` rows through `eval.matrix.arms.rrf`.
3. Run `python -m eval.matrix.run report OUT` with the five `--pair`
   arguments of the table.
